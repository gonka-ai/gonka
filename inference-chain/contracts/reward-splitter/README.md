# reward-splitter

Minimal push-only immutable payment splitter for redistributing mined epoch
rewards on Gonka. `ngonka` sent to the contract address is divided among a fixed
set of payees proportionally to fixed shares whenever anyone calls `Distribute`.

The whole contract is one file — `src/lib.rs` — so it can be pasted as-is into
the Gonka Contract Playground. Its own doc comment is the authoritative
description of the semantics; this file covers building, testing and deploying
it on this chain.

## Why immutable instances

No admin, no owner, no update message, and **no `migrate` entry point**.
Instantiated with `--no-admin`, an instance is frozen forever: the payee list
cannot change and the code cannot be swapped out. That is what makes
`Distribute` safe to leave permissionless — funds can only ever reach the
addresses fixed at instantiation, so a caller gains nothing beyond paying gas.

Instances are cheap and disposable: one `code_id`, a fresh instance per epoch or
per payee set. That matters, because storing code is what costs real resources —
see *Cost* below.

## Chain-specific caveats

These are properties of Gonka, not of the contract, and they decide whether the
design works at all:

- **A bank transfer to a contract does not execute it.** CosmWasm has no entry
  point for incoming coins. Rewards routed here (via `MsgSetClaimRecipients`, via
  `x/streamvesting` unlocks, or by hand) simply sit on the balance until someone
  cranks `Distribute`. Nothing is lost; the payout is not automatic.
- **`x/restrictions` can block the payout.** `SendRestrictionFn` permits only
  gas payments, transfers to or from a *module* account, and registered
  emergency exemptions. A contract account is a `BaseAccount`, so paying the
  contract *from* a module is always allowed, while the contract paying its
  payees out is a user-to-user transfer and is rejected while the restriction
  is active. On mainnet it is not: `restriction_end_block` is 1385263 and the
  chain is well past it. On any chain that is not — a fresh devnet, or the
  1555000 in this repo's genesis file — an instance needs an
  `emergency_transfer_exemptions` entry from governance. Check with
  `inferenced query restrictions status`.

## Messages

```jsonc
// instantiate — 1..=120 unique addresses, every share > 0
{"payees": [{"address": "gonka1…", "shares": 7}, {"address": "gonka1…", "shares": 3}]}

// execute — permissionless; funds may be attached to the call
{"distribute": {}}

// query
{"split": {}}   // → {"payees": [...], "total_shares": 10}
```

Each payee receives `floor(balance × shares / total_shares)`. The remainder —
strictly less than the payee count — stays on the contract and is re-absorbed
into the next distribution, so dust never accumulates.

## Build

```bash
./build.sh   # reproducible build via cosmwasm/optimizer:0.16.1 → artifacts/
```

The pinned toolchain is not a convenience. Modern Rust emits post-MVP wasm (bulk
memory) that wasmvm rejects at `tx wasm store` with *"bulk memory support is not
enabled"*, and `RUSTFLAGS="-C target-cpu=mvp"` does **not** help, because those
opcodes come from the precompiled `core`/`alloc`. The alternative, if you would
rather not run Docker, is Rust ≤ 1.81 followed by
`wasm-opt -Os --signext-lowering`, as noted at the top of `src/lib.rs`.

`Cargo.lock` must be generated by the same toolchain that does the final build.
The optimizer ships Cargo 1.81, which cannot parse `edition2024` manifests; a
lock refreshed by a recent Cargo pulls such crates in transitively and the build
fails. Pins that keep it working: `zeroize 1.8.1`, `zeroize_derive 1.4.2`,
`rmp 0.8.14`, `rmp-serde 1.3.0`.

## Verifying what is on chain

The chain identifies code by the SHA-256 of the wasm bytes — `Keeper.create`
stores it in `CodeInfo` and emits it as the `code_checksum` attribute of the
`store_code` event. It is independent of the `code_id`, of who uploaded it, and
of the machine that built it, so it is the one value worth quoting in a review:

```bash
sha256sum artifacts/reward_splitter.wasm   # what this repo ships
inferenced query wasm code-info <CODE_ID>       # what the chain stored: data_hash
```

The optimizer writes the same digest to `artifacts/checksums.txt`, which is
committed alongside the artifact.

Reproducing it requires three things to match: the optimizer image, the source,
and `Cargo.lock`. **Including the image's architecture** — `cosmwasm/optimizer`
(amd64) and `cosmwasm/optimizer-arm64` produce different bytes from identical
input. The committed artifact is built with the amd64 image; on Apple Silicon it
runs under emulation, which is correct — pulling the arm64 image instead yields
a different, equally valid checksum that simply will not match this one.

## Deploy

```bash
inferenced tx wasm store artifacts/reward_splitter.wasm \
    --from <key> --gas 40000000 --yes

inferenced tx wasm instantiate <CODE_ID> \
    '{"payees":[{"address":"gonka1…","shares":7},{"address":"gonka1…","shares":3}]}' \
    --label "reward-splitter" --no-admin \
    --from <key> --gas 5000000 --yes

inferenced tx wasm execute <CONTRACT> '{"distribute":{}}' --from <key> --gas 5000000 --yes
inferenced query wasm contract-state smart <CONTRACT> '{"split":{}}'
```

Storing code needs far more gas than the CLI default.

## Cost

The bytecode does not live in consensus state: only ~100 bytes of `CodeInfo` do.
The blob itself goes to every node's wasmvm cache, content-addressed by checksum
— measured at ~2.5 MB per distinct code (the raw wasm plus its compiled module),
replicated network-wide. Instantiating from an existing `code_id` costs ~200
bytes of `ContractInfo` plus the instance's own storage.

Hence the design: store once, instantiate freely.
