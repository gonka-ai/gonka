# Subnet Testenv

A self-contained test environment for running the subnet **without** `decentralized-api` or a live Cosmos chain.

- **10 participants** (configurable) running as Docker containers
- **16 slots** distributed round-robin across participants
- **Mock mainnet gRPC server** — handles escrow queries and settlement, no chain needed
- **docker-compose generated from a single config file**

---

## Purpose

The subnet testenv exists to **decouple subnet development from any external blockchain dependency** — mainnet, testnet, or testermint. Instead of fighting infrastructure to test a single protocol change, you spin up the entire subnet locally in under a minute.

### What it unblocks

| Problem | Solution |
|---------|----------|
| Need a live chain to get escrow data | Mock gRPC server answers all chain queries from local config |
| Testermint is flaky / slow to reset | No chain at all — escrow is pre-seeded in memory |
| dapi couples inference engine to subnet | `subnethost` uses stub engines; no ML node required |
| Hard to reproduce gossip/consensus bugs | 10 deterministic participants with fixed keys and IPs |

### Primary use cases

- **Gossip protocol** — observe nonce/tx propagation across all 10 participants
- **Consensus and finalization** — test phase transitions (Active → Finalizing → Settlement) end-to-end
- **Settlement verification** — validate quorum signature collection and on-chain submission logic against the mock server
- **Crash recovery** — kill and restart individual participants; verify session replay from SQLite storage
- **Internal devshard features** — any feature that touches subnet internals without needing a real chain

### Planned: observability stack (OTel)

The testenv will introduce **OpenTelemetry instrumentation** across all subnet components to make the internal message flow visible. The target stack is:

```
subnethost / mockserver
      │  OpenTelemetry SDK (traces, metrics, logs)
      ▼
   Alloy          ← OTel collector / log scraper
      │
  ┌───┴──────────────────┐
  ▼                      ▼
Tempo                VictoriaMetrics
(distributed traces) (time-series metrics)
      │                      │
      └──────────┬───────────┘
                 ▼
             Grafana
          (dashboards)
              +
            Loki
         (log aggregation)
```

Instrumentation targets:
- **Trace**: per-inference lifecycle (start → confirm → finish → validation → reveal → settlement)
- **Trace**: gossip message propagation path (which participant forwarded which nonce)
- **Metrics**: diff apply latency, quorum size over time, missed/invalid slot counters
- **Logs**: structured JSON from all containers, correlated with trace IDs via Alloy

## How it works

```
subnet/testenv/
├── proto/mockchain.proto          # gRPC service definitions (source of truth)
├── mockchain/                     # Go stubs generated by protoc (DO NOT EDIT)
│   ├── mockchain.pb.go
│   └── mockchain_grpc.pb.go
├── config/
│   ├── config.go                  # Config structs + load/save helpers
│   └── default.yaml               # Template config (10 empty participants)
├── bridge/grpc.go                 # GRPCBridge — implements MainnetBridge via mock server
├── cmd/
│   ├── gencompose/main.go         # Generates docker-compose.yml from config.yaml
│   ├── mockserver/main.go         # Mock mainnet gRPC server binary
│   └── subnethost/main.go         # Standalone subnet participant binary
├── Dockerfile.mockserver
├── Dockerfile.subnethost
└── Makefile
```

### Component roles

| Component | What it does |
|-----------|-------------|
| `mockserver` | In-memory gRPC server that pre-seeds the escrow from config. Answers `GetEscrow`, `GetParticipant`, `GetGrantees` queries and validates `SettleEscrow` calls. |
| `subnethost` | One instance per participant. Connects to the mock server via `GRPCBridge`, runs the full subnet host logic with stub inference/validation engines. |
| `gencompose` | One-shot tool: reads `config.yaml`, generates secp256k1 keys per participant, derives addresses, assigns slots, writes `docker-compose.yml`. |
| `subnetctl` | Existing user-side proxy (in `subnet/cmd/subnetctl/`). Connects to the testenv using `GRPCBridge` pointed at `mock-server:9090`. |

### Private keys — one per participant

Each participant has its **own** secp256k1 private key. The key is the identity of the participant:

- The key determines the participant's **blockchain address** (`gonka1…`)
- That address is placed in the escrow's **slot list** on the mock server
- When `subnethost` starts, it calls `GetEscrow` → sees its own address in the slot list → acts as a validator for those slots

`gencompose` generates a unique key for each participant and writes it into `config.yaml` and into each container's `TESTENV_PRIVATE_KEY` env var in `docker-compose.yml`.

### Where docker-compose.yml is generated

Running `make gen-compose` inside `subnet/testenv/` produces:

```
subnet/testenv/docker-compose.yml   ← generated (gitignored)
subnet/testenv/config.yaml          ← updated with keys + addresses (keep this!)
```

The generator (`cmd/gencompose`) reads `config.yaml`, fills in missing keys, and writes the compose file to the same directory. You can override both paths:

```bash
make gen-compose CONFIG=my-config.yaml COMPOSE=my-compose.yml
```

### Network layout (generated)

```
172.30.0.0/24
  172.30.0.2    mock-server    (gRPC :9090, HTTP status :9091)
  172.30.0.10   participant-0  (HTTP :8080, slots 0,10)
  172.30.0.11   participant-1  (HTTP :8080, slots 1,11)
  …
  172.30.0.19   participant-9  (HTTP :8080, slots 9)
```

## Quick start

All commands run from `subnet/testenv/`.

### 1. Copy and edit the config template

```bash
cd subnet/testenv
cp config/default.yaml config.yaml
```

The template has 10 empty participant slots and 16 slots. Edit to taste:

```yaml
# config.yaml
escrow_id: "1"
slots: 16          # total slot count (must be >= participant count, <= 128)
amount: 1000000    # escrow token amount
token_price: 1

participants:      # leave private_key_hex empty → gencompose auto-generates
  - {}
  - {}
  # ... 8 more

network:
  subnet: "172.30.0.0/24"
  base_ip: "172.30.0"

mock_server:
  port: 9090
  ip: "172.30.0.2"
  name: "mock-server"
```

To change participant count, add or remove `- {}` entries. To pre-set a key:

```yaml
participants:
  - private_key_hex: "your64hexcharshere..."  # optional; derived address will be filled in
  - {}   # auto-generated
```

### 2. Generate keys and docker-compose

```bash
make gen-compose
```

This:
1. Generates a secp256k1 private key for each empty participant
2. Derives each participant's `gonka1…` address
3. Assigns slots round-robin (`slot i → participant i % N`)
4. Writes `docker-compose.yml` with static IPs and `TESTENV_PRIVATE_KEY` env vars
5. Saves the filled-in `config.yaml` (commit this to track your testenv)

After this step `config.yaml` looks like:

```yaml
participants:
  - private_key_hex: "838f6b5aa96c70503c44bc..."
    address: "gonka1klw5s08vxp2nculcy7tpu76vzwl8y3eytkza60"
    slot_ids: [0, 10]
    name: participant-0
    ip: 172.30.0.10
    port: 8080
  - private_key_hex: "dd8cdd59ae3a81628c98e9..."
    address: "gonka13t9kaeawaymre60qa82wghg4uwsx655mpqfh9l"
    slot_ids: [1, 11]
    name: participant-1
    ip: 172.30.0.11
    port: 8080
  # …
```

### 3. Build Docker images

```bash
make build
```

This builds:
- `subnet-mockserver:latest` — from `Dockerfile.mockserver`
- `subnet-host:latest` — from `Dockerfile.subnethost`

### 4. Start the network

```bash
make up
```

Wait a few seconds, then verify:

```bash
# Mock server health
curl http://localhost:9091/health    # → "ok"
curl http://localhost:9091/status   # → escrow/participant summary

# Participant health (exposed on host via docker-compose port mapping)
# Note: ports are not mapped by default; exec into the network instead
docker exec -it participant-0 wget -qO- http://localhost:8080/health
```

### 5. Run a user session with subnetctl

`subnetctl` (in `subnet/cmd/subnetctl/`) acts as the user-side proxy. Point it at the
mock server for mainnet queries and at the participant hosts for inference.

Build subnetctl:

```bash
cd ../..   # back to subnet/
go build -o subnetctl ./cmd/subnetctl
```

Run it inside the docker network (or map ports in `docker-compose.yml` first):

```bash
SUBNET_CHAIN_REST=http://localhost:9090   # mock server REST-compatible endpoint (not yet wired, use GRPCBridge directly)
SUBNET_ESCROW_ID=1
SUBNET_PRIVATE_KEY=<any-secp256k1-hex-key>
SUBNET_PORT=8888
./subnetctl --escrow-id=1 --chain-rest=http://mock-server:9090 --port=8888
```

> **Note:** `subnetctl` currently uses `RESTBridge`. To use `GRPCBridge` with the mock server,
> wire it via the `GRPCBridge` in `subnet/testenv/bridge/grpc.go`. This is the preferred path
> for testenv integration.

### 6. Dev mode (live reload + debugger)

See `DEVELOPMENT-MODE.md` for the full workflow, commands, debug ports, and how
`docker-compose.dev.yml` overrides the base stack.

### 7. Finalize and settle

1. Send a chat request to trigger an inference round:
   ```bash
   curl -s http://localhost:8888/v1/chat/completions \
     -H "Content-Type: application/json" \
     -d '{"model":"stub","messages":[{"role":"user","content":"hello"}]}'
   ```

2. Finalize the round:
   ```bash
   curl -s http://localhost:8888/v1/finalize
   # Returns the SettlementPayload JSON
   ```

3. Submit settlement to the mock server (via a tool or script using `GRPCBridge.SubmitSettlement`).
   The mock server runs `state.VerifySettlement` to check the quorum of slot signatures before
   marking the escrow settled.

4. Check escrow status:
   ```bash
   curl http://localhost:9091/status
   ```

## Configuration reference

| Field | Default | Description |
|-------|---------|-------------|
| `escrow_id` | `"1"` | ID returned by `MockQuery.GetEscrow` |
| `slots` | `16` | Total slot count; must be ≥ participant count |
| `amount` | `1000000` | Escrow token amount |
| `token_price` | `1` | Token price used in `SessionConfig` |
| `app_hash` | sha256("testenv") | 32-byte hex; embedded in escrow info |
| `participants[*].private_key_hex` | auto-generated | secp256k1 key hex; leave empty to auto-generate |
| `participants[*].port` | `8080` | HTTP listen port inside container |
| `network.subnet` | `172.30.0.0/24` | Docker network CIDR |
| `network.base_ip` | `172.30.0` | First three octets; mock server gets `.2`, participants start at `.10` |
| `mock_server.port` | `9090` | gRPC listen port; HTTP status at port+1 (`9091`) |

To add participants, add more `- {}` entries under `participants:` and re-run `make gen-compose`.

## Regenerating gRPC stubs (`mockchain/` from `proto/`)

The two files in `mockchain/` are **auto-generated** — do not edit them by hand:

```
proto/mockchain.proto          ← source of truth (edit this)
        │
        │  protoc
        ▼
mockchain/mockchain.pb.go      ← message types   (generated by protoc-gen-go)
mockchain/mockchain_grpc.pb.go ← client/server stubs (generated by protoc-gen-go-grpc)
```

### Install the code-generation tools

```bash
# protoc — the Protocol Buffers compiler
# macOS
brew install protobuf

# Ubuntu / Debian
apt install -y protobuf-compiler

# Verify
protoc --version   # libprotoc 3.x or later

# Go plugins (install once into $GOPATH/bin)
go install google.golang.org/protobuf/cmd/protoc-gen-go@latest
go install google.golang.org/grpc/cmd/protoc-gen-go-grpc@latest

# Verify they're on PATH
which protoc-gen-go
which protoc-gen-go-grpc
```

### Regenerate

From `subnet/testenv/`:

```bash
make proto
```

Under the hood this runs:

```bash
protoc \
  --proto_path=proto \
  --go_out=mockchain        --go_opt=paths=source_relative \
  --go-grpc_out=mockchain   --go-grpc_opt=paths=source_relative \
  proto/mockchain.proto
```

`paths=source_relative` means the generated package is `mockchain` (matching the directory), not a nested path derived from the proto package name.

### When to regenerate

Regenerate any time you change `proto/mockchain.proto` — adding a new RPC, adding a field to a message, etc. After regenerating, the `GRPCBridge` (`bridge/grpc.go`) and mock server (`cmd/mockserver/main.go`) may need updating to implement any new methods.

### What the generated files contain

| File | Contents |
|------|---------|
| `mockchain.pb.go` | Go structs for every `message` in the proto (`GetEscrowRequest`, `SettleEscrowRequest`, etc.) with protobuf serialization logic |
| `mockchain_grpc.pb.go` | `MockQueryClient` / `MockTxClient` interfaces + `grpc.Dial`-based implementations (used by `GRPCBridge`); `MockQueryServer` / `MockTxServer` interfaces (implemented by `mockserver`) |

## Architecture notes

- **Slot assignment**: `slot i → participant i % N` (round-robin). With 16 slots and 10 participants, participants 0–5 get 2 slots each; participants 6–9 get 1 slot each.
- **Escrow addresses vs participant IPs**: The escrow `slots` array contains each participant's blockchain address (`gonka1…`). When a host queries `GetParticipant(address)`, the mock server returns `http://participant-N:8080` — the Docker DNS name. This is how the subnet connects blockchain identity to network location.
- **Warm key verification**: `GetGrantees` returns all participant addresses, so warm-key checks always pass in the testenv.
- **Stub engines**: `subnethost` uses `stub.InferenceEngine` and `stub.ValidationEngine` from `subnet/stub/`. No ML node is required.
